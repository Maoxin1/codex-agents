# 现有三位 agent 的设计优化评审

状态：待验证的设计建议。本文不改变 `_mantou`、`_factbot`、`_invest` 的运行规则。

本评审依据仓库现有配置、支持规范和行为案例，检查[五位书籍顾问设计](book-advisors-design.md)能提供哪些启发。
下文是本项目的设计推导；尚未逐条完成新增四本书的原文核验，不能将建议称为作者意见。
优先复用已存在的能力，再找能改变实际结果的缺口。

## 1. 先拷问这次优化

### 是否把同样的能力换个名字当作新增？

`_mantou` 已要求保留原意和约束；`_factbot` 已检查来源独立性、反证和检索停止条件；`_invest` 已有证伪条件、复核触发器和情景。
新增这些口号不会带来收益。候选优化需要指出现有规则在哪个真实场景仍不足，并提供能区分修改前后的案例。

### 是否让每位 agent 都承担研究、教学和调度？

统一学习体验不等于统一职责。`_mantou` 的输出是可直接使用的提示词，其现有契约禁止研究和解释；不应强加教学尾注。
`_factbot` 的价值在于事实与证据核验；`_invest` 的价值在于正式投资研究与论点维护。
新方法应作为设计工具，避免默认加载五本书或自动召集五位顾问。

### 是否增加了超过收益的流程？

每项建议先看能否在现有回答中增加一句有用的判断，而不是增加一个表格或一次调用。
没有行为差异或实用收益的改动应撤回。来源追溯、确认机制和外部行动边界各有职责，不因“更快”而合并或取消。

## 2. `_mantou`：提升下游任务的可完成性

现状依据：[配置](../agents/_mantou.toml)、[行为案例](../agents/_mantou/tests/cases.json)。

已经具备：保留意图、事实、资源、权限与约束；仅做有价值的澄清；用占位符表达缺失信息；强提示词保持接近原文；保留下游执行步骤；仅返回成品并校验剪贴板。

| 候选改进 | 具体变化 | 验收案例 |
|---|---|---|
| 检查问题是否预设结论 | 对明确的开放研究任务，避免把“调查是否成立”改成“证明成立”；明确要求的立场保留为任务约束 | “调查新功能是否提高留存”改写后仍允许无效或负面结果 |
| 区分目标和指定手段 | 用户明确给出目标时保留其与手段的关系；手段作为硬约束时继续保留；材料缺失时使用占位符 | “用 Redis 降低查询延迟”保留 Redis，不擅自换架构，也不凭空断言瓶颈 |
| 让交付可检查 | 对“优化、完善、分析”等开放任务，在已有意图范围内明确产物和验收占位符 | “优化首页”可要求填写目标与验收信号，不凭空设置提升 20% |
| 用效果评估提示词 | 将成品用于合成下游任务，比较关键约束遗漏与无依据假设 | 原提示词已清晰时，改写不增加无关流程；执行顺序完整 |

拷问：用户要的可能是快速转交任务，是否值得多一段教学或自动研究？目前答案是否定的；保留输出与剪贴板契约。
占位符和意图保留本来就存在，本次重点是针对开放研究、目标与手段、可验收性交互的边界案例，而非宣称新增全部能力。

预期调用示例（现有能力即可使用）：

```text
请调用 _mantou 优化：检查这个缓存方案是否能降低查询延迟，保留指定技术约束和不确定性。
```

## 3. `_factbot`：把核验资源用于会改变判断的主张

现状依据：[配置](../agents/_factbot.toml)、[行为案例](../agents/_factbot/tests/cases.json)。

已经具备：拆分主张、核查预设、补充口径、评价来源、识别共同上游、寻找反证、区分未找到与被反驳、停止条件、错误修正和认知结论与行动建议分离。

| 候选改进 | 具体变化 | 验收案例 |
|---|---|---|
| 优先核验关键依赖 | 多主张任务中先标明哪些主张若不成立会改变总判断，再选择检索顺序 | 十条宣传中一条直接决定兼容性，优先核验这一条；其他未核验项明确说明 |
| 组织可区分的证据 | 将“还缺证据”细化为缺失材料及其能区分的候选解释 | 安全事件原因存在两种解释时，说明哪份日志能区分；不默认索取所有日志 |
| 让停止理由可见 | 将已有停止规则落实为简短的覆盖范围与停止原因，复杂核验时保留来源依赖关系 | 多篇转载没有新增独立信息时停止，并说明哪项仍未证实 |
| 记录结论修订 | 对持续核验保留旧判断、新证据、变更范围与日期；私有记录的写入由获授权主体处理 | 新证据仅推翻一个子主张时，不无依据推翻全部结果 |

拷问：一句已证实事实是否足够支持用户要做的决定？核验只支持对应的事实范围；行动还依赖目标、成本和风险。
反过来，用户未说明用途时，不能为收集用途而阻塞普通事实核验。用户已提供用途时再据此安排核验优先级。
这些建议主要使现有规则更可检查，而非新增“来源独立性”或无限扩大调查。

预期调用示例（现有能力可处理，优先级细化仍待评估）：

```text
请调用 _factbot 核验这份供应商材料。我们最关心离线运行与数据导出是否成立。
先核验会改变选型的主张，列出其余尚未检查的内容。
```

## 4. `_invest`：把研究重点放在能改变论点的未知量

现状依据：[运行核心](../agents/_invest/core.md)、[任务路由](../agents/_invest/workflow.md)、[证据规范](../agents/_invest/evidence.md)。

已经具备：任务确认、证据标签、来源冲突处理、行业指标、市场隐含预期、反方、基准率、情景、证伪条件、复核触发器、历史快照、机会成本与研究行动分层。

| 候选改进 | 具体变化 | 验收案例 |
|---|---|---|
| 明确改变判断的研究问题 | 在已确认范围内选出一至三个答案不同就会改变论点的未知量，研究按其组织 | 资料充足但留存假设决定估值时，优先核查同口径留存及其持续性 |
| 用用户需求挑战商业叙事 | 将管理层“产品领先”拆成用户情境、替代方案和行为证据，再连接收入质量与现金流 | “AI 产品受欢迎”须检查付费、续费、替代和成本；不能直接推出护城河 |
| 标出证据到估值的连接 | 在现有论点地图中明确证据改变哪个经营假设、影响哪个情景和价值区间 | 收入增长伴随获客成本恶化时，同时检查盈利和现金流，不只上调增长 |
| 优先安排有价值的补充研究 | 比较新增证据能改变什么、取得难度及剩余不确定性，用定性排序安排研究 | 已能形成条件式结论时，说明继续查证的价值，不伪造信息价值概率 |

拷问：用户理解越充分，投资结论就越可靠吗？客户需求只是商业研究的一部分，还需财务、治理、竞争、资本结构和价格证据。
JTBD 适用程度也因行业而异，不能强行把商品周期、金融资产或资本配置问题套成用户访谈。

正式任务的确认状态机继续有效。用户改变范围、启动新的正式研究、修改论点或写入知识库时，按现有约定确认。
“即时学习”不能作为绕过确认的入口；纯概念问答是否单独提供轻量模式，留待用户确认与独立评估，不在本轮改变。

预期调用示例（仍须先复述并等待正式任务确认）：

```text
请调用 _invest 复核这家公司的原始论点。
重点找出最可能改变判断的三个未知量，以及新证据将改变哪些假设和情景。
```

## 5. 优先级与实施门槛

优先做三件事：为 `_mantou` 增加保留可证伪性与验收边界的案例；让 `_factbot` 的关键主张顺序及停止理由可检查；让 `_invest` 的关键未知量与经营假设、估值连接更清楚。
解释性教学、持续记忆、自动联合调用和专门的新模式均不随本轮文档上线。

每项候选改动先使用三个合成案例比较现有版与候选版：一个明显适用、一个边界情境、一个无需改变的任务。
先检查现有版能否满足案例，出现可定位失败后才修改规则。候选版须修复该失败、在约束完整性、证据清晰度或下一步可执行性上有具体改善，并通过原有契约回归后再试用。
记录等待时间、回答长度、遗漏和用户是否采纳；收益不足时简化或撤回。
小规模案例用于发现问题，不能证明总体可靠，也不能代替原有完整回归检查。

实现任何契约变化时同步更新配置、支持文档、验证资产和变更记录。
已补充[针对性行为案例](agent-pilot-cases.md)，未运行付费行为评估；现有运行配置保持原状。没有具体失败证据前，不为这三位新增规则。
