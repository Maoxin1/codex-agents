# 组织研究

## J01 — 界定范围

来源：第 2 章 Putting It All Together: Scope the JTBD Domain；定位 `text:Putting It All Together: Scope the JTBD Domain`。
明确主任务、执行者，并对过程和情境形成可修订的假设。范围和抽象层级须结合团队要解决的问题，并尽早与实际执行者接触。
适用：团队讨论的对象和粒度不一致。局限：初始定义是研究起点，不是已经确认的客户事实；不必等到完美措辞才开始。
应用推导：先限定“维护者复现线上故障”，把排查过程列作待查假设，避免一次研究所有开发活动。

## J02 — 访谈与证据整理

来源：第 3 章 PLAY Conduct Jobs Interviews、Analyze the Data；定位 `text:PLAY Conduct Jobs Interviews`、`text:Analyze the Data`。
接触实际执行任务的人，开放询问其目标和过程。分析时保留直接观察与原话，再整理为任务、需求和情境等解释，避免失去原始依据。
适用：把零散访谈交给团队讨论。局限：采购者不一定是执行者，访谈不是读心；记录或转录需遵守用户已有授权。
应用推导：在只读交付中列“摘录位置—解释—未知项”；没有原话时不制造引文，标明只是摘要或假设。

## J03 — 两种访谈入口

来源：第 3 章 PLAY Run Switch Interviews；定位 `text:PLAY Run Switch Interviews`。
Jobs 访谈着重理解任务执行和需要；Switch 访谈还原为何从一种方案转向另一种。后者围绕具体选择过程回顾事件，方法归属 Bob Moesta 与 Chris Spiek。
适用：选择招募对象和访谈方向。局限：B2B 的购买者与使用者可能不同，购买故事不能自动代替执行者的需要。
应用推导：若问题是“为何买了却不使用”，分别向购买者和实际使用者寻找相关材料，而不是默认一份访谈解释全部。

## J04 — 任务地图

来源：第 3 章 PLAY Map the Main Job；定位 `text:PLAY Map the Main Job`。
组织完成主任务的阶段性目标，尽量不锁定具体技术和手段。书中介绍的通用阶段是检查清单，可按任务调整，不是强制八步流程；不同于产品购买或消费旅程。
适用：从访谈寻找任务前、中、后的遗漏。局限：不能把界面点击步骤换个名字就当作任务地图，也不能只凭想象宣称完成地图验证。
应用推导：先整理“取得故障信息—形成解释—检验修复”等暂定目标，再标注各阶段来自哪些访谈。
